# 决策：配置字段的方言化方案选型

- **日期**：2026-09-22
- **决策人**：插件维护者
- **状态**：已选定（方案 B），附升级触发条件

## 背景

`ConnectionProfile` 目前的字段是 MySQL 形状：`host / port / user / database / passwordEnv / connectTimeoutMs / queryTimeoutMs / maxRows`。
新增方言时会出现两类冲突：

1. **字段不够**：Oracle 需要 service name 或 SID，MongoDB 需要连接串，SQLite 只需要文件路径。
2. **字段多余**：SQLite 没有 host/port/user，要求用户填 3306 是噪音。

## 候选方案

### 方案 A：字段完全由方言声明

profile 变成 `{ id, name, dialect, config: Record<string, string | number>, limits }`，页面字段全部来自 `dialect.configFields()`。

- 优点：彻底；任何形态的数据库都能表达。
- 缺点：**破坏性变更**。已保存的连接文档、组合层 `cordis.yml` 平铺字段、设置页表单、宿主 schema 全部要迁移；也给「跨方言切换」制造成本。

### 方案 B：通用字段 + 方言扩展字段（选定）

保留 `host / port / user / database / passwordEnv` 作为**通用连接字段**（绝大多数 SQL 数据库都有），新增：

```ts
interface ConnectionProfile {
  // …既有通用字段…
  /** 方言声明的额外连接字段，按方言的 configFields 键取值。 */
  extra: Record<string, string | number>
}
```

方言通过 `configFields: readonly DialectConfigField[]` 声明额外字段，页面在选中该方言时渲染它们，值落在 `extra` 里。

- 优点：既存配置零迁移；页面与宿主 schema 增量修改；覆盖 Oracle（service name）、MongoDB（连接串）等绝大多数诉求。
- 缺点：对「连 host/port 都不存在」的方言（SQLite）仍会渲染无用字段。

## 选定理由

1. 兼容性优先：本插件已有真实用户配置，方案 A 的迁移成本高于当前收益。
2. 增量交付：方案 B 可在 M3 独立完成，不阻塞 M1/M2。
3. 方案 A 的能力在方案 B 里没有丢失——只是延后。

## 升级到方案 A 的触发条件

出现下列任一情况时，重新评估并迁移到方案 A：

- 需要支持**无 host/port 概念**的方言（SQLite、DuckDB、本地文件型库）；
- 通用字段在两个以上方言里被证实是噪音；
- 连接文档格式因其他原因必须做一次破坏性升级（可搭车迁移）。

## 补充决策（同日）：宿主包必须声明为「可选」peer

第一版把 `@deepseek-ai/*` 写进 `peerDependencies` 后，`pnpm install` 直接失败：这些包尚未发布到 npm，包管理器会去仓库解析它们。

修正：全部标记 `peerDependenciesMeta.*.optional = true`。语义上也正确——它们由宿主运行时提供，缺失与否不该由包管理器决定。

**给方言作者的同样规则**：声明 `"peerDependencies": { "dsh-ds-db": ">=0.2.0" }` 时，若目标未发布，安装需加 `--legacy-peer-deps`（示例包 README 已写明）。

## 迁移预案（届时执行）

1. `contract.ts` 增加 `config` 与 `limits`，保留旧字段为可选；
2. 宿主 `installSection` 的 schema 同时接受新旧两种形状；
3. 首次读取时把旧字段升维进 `config`（读时迁移，不写回，避免 revision 冲突）；
4. 两个大版本后移除旧字段。
